# Direct PDF reading and assessment verification

KalaBASA now uses its existing local PDF.js dependency to read usable embedded PDF text. Tesseract runs only when the page has no usable text layer; PNG/JPG uploads still use OCR. Both paths retain page images for human inspection. No cloud PDF reader or AI service is used.

The reader records `textSource: pdf_text` or `ocr` per page. Native PDF text has no OCR confidence score, so its confidence is `null`, not an invented percentage. Being readable does not establish authenticity: a PDF's text layer can differ from its visible content, and signatures/seals still require human review.

The local model returns a smaller JSON object containing field values. The backend locates each value in the source and builds the evidence quote itself. Unsupported values are discarded. Only case/Unicode/whitespace differences can be reconciled; the retained value uses the source's spelling. This avoids generated quote errors and reduces output tokens. Document headings establish types independently of whether model extraction succeeds. A checklist listing attached documents does not establish those document types.

Requirements can optionally configure `extractFields` for each document type. This keeps unlike identifiers separate—for example, a TIN on an application is not a DTI registration number. It also avoids treating a personal residence on a cedula as a business address. Optional `fieldScopes` restrict a field to text between configured start/end markers: the sample lease policy uses the premises clause for business address and the lessee paragraph for owner name. A value outside its assigned section is discarded. These are template-specific extraction settings, separate from the core engine; other lease layouts may require different markers and otherwise need manual review.

The requirements screen separates compliance issues (confirmed rule violations or potential inconsistencies) from verification checks (unreadable/unrecognized data or checks requiring a person). A document whose type could not be verified is labelled **Unverified**, not definitely **Missing**. Repeated comparisons of the same field produce one issue with all supporting evidence retained.

`config/requirements.example-v2.json` is an updated **sample** checklist covering the application, DTI registration, barangay clearance, lease and cedula. It adds the lease to business-address comparison. This is not an official LGU policy and retains its sample-policy warning and authenticity review requirement.

Existing assessments retain their saved text, findings and policy snapshot. Use **Retry same checklist** to run the new reader with the original policy. Use **Reassess with current checklist** to explicitly use the LGU's active policy; the prior result is preserved in encrypted assessment history and the change is audited. Neither action submits the application to an LGU or records an approval.

Tests include native PDF reading with Tesseract deliberately unavailable, continued scanned-image/PDF OCR, evidence grounding, corrected document recognition, separate UI counters, and explicit policy-version changes on reassessment.

Validation on the five supplied demo PDFs completed in approximately 58 seconds with local Ollama and Tesseract deliberately disabled: all eight pages used PDF.js, the DTI certificate was recognized, and no documents were declared missing. The engine retained one potential business-address inconsistency (45 versus 54 MacArthur Highway), plus separate authenticity and sample-checklist verification checks. The lease's owner was correctly extracted from the lessee paragraph. All 25 automated tests passed. These measurements describe this small example set, not a general accuracy or throughput benchmark.

Source display was subsequently corrected and covered by 28 passing tests. Every extracted field includes document identity, an authenticated original-document URL and, when located, an authenticated page URL. An omitted historical page reference is recovered only if its saved quote/value matches exactly one saved page; ambiguous references remain document-level. No assessment data is rewritten by this display repair. Empty fields outside a document's configured extraction list are omitted, while required fields stay visible even if not extracted. Optional unextracted fields are neutral, not treated as violations. Checklist checks identify the applicable LGU rule rather than presenting duplicate empty document excerpts. Existing assessments receive these display corrections on refresh.
